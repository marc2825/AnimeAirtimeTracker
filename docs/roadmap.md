# ロードマップ

今後の開発の方針と優先度です。完了した変更は [CHANGELOG](../CHANGELOG.md)、個々の作業は Issue と Pull Request で扱います。

最終更新: 2026-11-22（公開サイト: <https://anime-airtime-tracker.vercel.app>）

## 実装済み

主な機能だけを挙げます。

- 週間番組表、検索（作品・放送・放送枠）、作品ページ、放送枠の年表、編成統計、データ更新状況。スマートフォンとダークモードに対応
- しょぼいカレンダーからの自動取得（6時間ごとの差分と毎日の直近の再取得）と、取得状況の公開
- 放送開始時刻による時間帯の絞り込み（「深夜アニメ」「24時以降」を含む）と、系列・放送時間の長さによる絞り込み。番組表・検索・統計で使える
- 統計の時間帯別の推移とクール間の比較
- クール別の新作一覧、放送局ページ、放送中のバナー
- 取得停止の監視（`/api/health` と毎日の確認、定期実行の維持）
- 毎月の暗号化バックアップ（同じジョブで復元して件数を照合）
- 2000年冬クール以降の過去データ（2005年以前は出典の登録が少なく、その旨を図と説明に表示）
- 放送枠の開始時刻の変化、年別の作品数、関連する枠の表示。放送枠の一覧で、各クールの作品名をホバー・タップで表示
- 公開サービスとしての整備（#22）: 存在し得ないURLの404、DB障害時の誤表示の防止、データ鮮度の表示、サイトマップの503、問い合わせ・プライバシーポリシー・利用規約、Actions とバックアップイメージの固定、CodeQL、障害対応と利用量の文書化
- アクセシビリティの自動確認: 主要13ページを、ライト・ダーク、PC・スマホで axe（WCAG 2.2 A/AA）にかけ、CI の E2E で毎回確認する

## 開発予定

優先度は利用者への価値と、規模・保守の負担から決めています。規模は S（数時間）/ M（数日）/ L（それ以上）の目安です。

| 項目 | 優先度 | 規模 | 内容 |
| --- | --- | --- | --- |
| 公式サイトへのリンクの拡充 | Medium | M | 作品ページの「公式サイト」欄は、出典の備考から抽出したURLを表示している（2024年以降の作品の約86%、2026年11月時点）。番組表・検索結果・放送枠の年表からも公式サイトへ移動できるようにし、記載のない作品は出典URL付きの上書き（`data/overrides.json`）で補う。リンク切れの確認は、外部サイトへのアクセスの扱いを決めてから行う。 |
| 公式枠の登録 | Medium | M | ノイタミナなど放送局が公表している枠を、出典URL付きで `data/slots.json` に登録する。 |

所有者の作業（任意。手順は [operations.md](operations.md)）:

- Google Search Console への登録（所有者の Google アカウントが必要）
- GitHub Actions から独立した外部監視（`/api/health` を監視するサービスのアカウントが必要）
- GitHub アカウントなしで連絡できる窓口（専用メールまたはフォーム。選択肢と、決めたときに直す箇所は operations.md）
- 推奨設定: `main` のルールセット、`DIRECT_DATABASE_URL` を `production` 環境へ移すこと
- プライバシーポリシー・利用規約の法的な文面の確認

## 検討中

- 放送時刻の変更の見せ方。作品ページは変更回数だけを表示している。変更前後の時刻を示すか、番組表で直近に変わった放送を目立たせる。
- スマートフォンでの検索条件の簡素化。詳細条件の7項目が縦に並ぶため、よく使う条件だけを先に出す。
- 放送枠ごとのクール間の比較（統計ページの比較は局・時間帯単位）。
- データ量やアクセスが増えたときの作品検索の高速化（`pg_trgm`）と永続キャッシュ。
- 中京圏など対象地域の追加、推定枠の時刻移動の追跡、統計表のCSV出力、予定と実績の比較。

## 保留・見送り

- 英語UI: 需要が確認できるまで保留する。
- JavaScript 無効時のデータ表示: データはストリーミングで描画され、差し替えに JavaScript が必要なため対応しない。読み込み中の代わりに案内を表示する。
- 認証付きの管理画面: 運用はCLIとGitHub Actionsで行う方針のため作らない（[architecture.md](architecture.md)）。
- 時間帯を「放送中」で判定する方式（帯の前に始まり帯にかかる放送も含める）: 開始時刻で判定するほうが検索・統計と一致し、説明もしやすいため採用しない。
- Lighthouse の CI 実行: アクセシビリティは axe で毎回確認しており、性能の点数は CI の実行環境で大きく揺れるため、閾値で合否を決める用途に向かない。性能は本番相当データでの実測（operations.md の Capacity and limits）で見る。
- 主要画面の画像比較（スクリーンショットの差分テスト）: フォントの描画が CI とローカルで異なり、基準画像の維持に手間がかかる割に誤検知が多いため見送る。画面の確認は `npm run screenshots` での目視レビューを続ける。
- バックアップの週次化: 1回の取得で Neon の転送量を数百MB使うため、無料枠では月次を維持する（理由と見直す条件は operations.md）。
