# ロードマップ

今後の開発の方針と優先度です。完了した変更は [CHANGELOG](../CHANGELOG.md)、個々の作業は Issue と Pull Request で扱います。

最終更新: 2026-11-22（公開サイト: <https://anime-airtime-tracker.vercel.app>）

## プロダクトの方針

アニメ放送枠観測所は、一般的なアニメ情報サイト・番組表サイトではなく、**日本のテレビアニメの放送枠と放送編成の歴史・変遷・統計を横断的に調べられる専門データベース**を主軸とする（#23）。

- 今日・今週の番組表は、日常的な利用の入口として維持・改善する。
- 他サイトとの違いは、蓄積したデータの体系化、公式枠と推定枠の区別、長期的な時系列分析、地域・局・曜日・時間帯の比較、再現可能な集計に置く。
- 対象外: 一般的な作品紹介、感想、視聴記録、配信情報の網羅。作品画像の転載や、根拠のない自動生成の記事も扱わない。
- データ取得元へのリクエストを増やさずに実現できる方法を優先する。数値や結論は実データから計算し、先に決めない。

## 実装済み

主な機能だけを挙げます。

- 週間番組表、検索（作品・放送・放送枠）、作品ページ、放送枠の年表、編成統計、データ更新状況。スマートフォンとダークモードに対応
- しょぼいカレンダーからの自動取得（6時間ごとの差分と毎日の直近の再取得）と、取得状況の公開
- 放送開始時刻による時間帯の絞り込み（「深夜アニメ」「24時以降」を含む）と、系列・放送時間の長さによる絞り込み。番組表・検索・統計で使える
- 統計の時間帯別の推移とクール間の比較
- クール別の新作一覧、放送局ページ、放送中のバナー
- 取得停止の監視（`/api/health` と毎日の確認、定期実行の維持）
- 毎月の暗号化バックアップ（同じジョブで復元して件数を照合）
- 2000年冬クール以降の過去データ（2005年以前は出典の登録が少なく、その旨を図と説明に表示）
- 放送枠の開始時刻の変化、年別の作品数、関連する枠の表示。放送枠の一覧で、各クールの作品名をホバー・タップで表示
- 公開サービスとしての整備（#22）: 存在し得ないURLの404、DB障害時の誤表示の防止、データ鮮度の表示、サイトマップの503、問い合わせ・プライバシーポリシー・利用規約、Actions とバックアップイメージの固定、CodeQL、障害対応と利用量の文書化
- 分析ページの基盤（`/analysis`、`src/analysis/`）: 対象・単位・出典・データ時点・定義・限界・確かめ方を共通の枠で示し、結論はデータから計算する。最初の分析「深夜アニメの長期的な変遷」
- 放送枠の比較（`/compare/slots`、#23）: 2〜4枠の概要（作品数、放送のあったクール、1クールあたりの作品数、平均の放送時間、開始時刻の変化）、開始時刻の推移、クール別の放送位置
- 地域・放送局の比較（`/compare/channels`、#23）: 地域か局を2つ選び、作品本数・23時以降の割合・最も多い曜日時台、クール別の推移、同じ色の基準の曜日×時間帯、共通の作品と同じ話数の放送時差（両方が受信する局は除く）
- 図の書き出しと共有（#23）: 統計・放送局・分析の図を CSV・SVG・PNG で書き出せる（出典・サイト名・対象範囲・URL・データ時点を記載）。「リンクをコピー」は、既定値に頼らず条件をすべて書いたURLを渡す
- 各話のサブタイトル: 出典の作品ごとの話数別一覧を取り込み、番組表・作品ページ・放送の検索結果に表示する。取得済みの作品は定期取得のたびに少しずつ取り直す（進捗は `/status`）
- 制作会社・出版社から見た暗黙の放送枠（実験）: 作品備考の「アニメーション制作」と掲載誌・原作の行から制作会社・出版社を取り込み、放送枠ごとの構成、1社が半数以上を占める枠、構成が似ている枠、次のクールの候補（過去のデータで測った的中率つき）を表示する（`/analysis/implicit-slots`、放送枠・作品ページ）
- アクセシビリティの自動確認: 主要13ページを、ライト・ダーク、PC・スマホで axe（WCAG 2.2 A/AA）にかけ、CI の E2E で毎回確認する

## 開発予定

優先度は利用者への価値と、規模・保守の負担から決めています。規模は S（数時間）/ M（数日）/ L（それ以上）の目安です。

| 項目 | 優先度 | 規模 | 内容 |
| --- | --- | --- | --- |
| 公式放送枠の整理 | High | M | ノイタミナ、アニメイズムなどの公式枠を放送局の一次情報で確認し、名称・局・期間・根拠を出典URL付きで `data/slots.json` に登録する。未確認の所属や移動は断定しない。 |
| 歴代放送枠のデータ充実 | High | M | クールごとの作品一覧、放送時刻・曜日の変更、枠の名称変更・休止・再開を年表で見やすくする。既存の年表を再利用する。公式放送枠の整理の後に行う。 |
| データ品質・再現性 | High | M | 観測範囲、欠損、推定根拠、集計条件を各ページで明示する。作品本数と放送件数、再放送、新作、局の重複を混同しない。集計条件とルールのバージョンを保存する。分析ページの「対象・単位・データ時点・定義・限界・確かめ方」は実装済み。 |
| 放送変更の履歴 | Medium | M | 観測した変更の前後の時刻と更新時点を表示する。観測した時点と実際の放送実績を区別する。 |
| 日常利用の入口 | Medium | S | 今日・今夜の深夜アニメ、曜日別・地域別・局別の番組表への導線。既存の絞り込みを使い、重複して作らない（カレンダー、曜日・地域のリンクは実装済み）。 |
| 公式サイトへのリンクの拡充 | Medium | M | 作品ページの「公式サイト」欄は、出典の備考から抽出したURLを表示している（2024年以降の作品の約86%、2026年11月時点）。番組表・検索結果・放送枠の年表からも公式サイトへ移動できるようにし、記載のない作品は出典URL付きの上書き（`data/overrides.json`）で補う。リンク切れの確認は、外部サイトへのアクセスの扱いを決めてから行う。 |

所有者の作業（任意。手順は [operations.md](operations.md)）:

  - Search Console で、トップページのURL検査とインデックス登録のリクエスト、`/sitemap.xml`（サイトマップインデックス）の再送信。
  - Bing Webmaster Tools への登録（Search Console からのインポート、または `BING_SITE_VERIFICATION`）と、サイトマップの送信。
  - 2〜4週間後に、サイト名・一般語での検索順位と「クロール済み - インデックス未登録」の内訳を再確認する。
- GitHub Actions から独立した外部監視（`/api/health` を監視するサービスのアカウントが必要）
- GitHub アカウントなしで連絡できる窓口（専用メールまたはフォーム。選択肢と、決めたときに直す箇所は operations.md）
- 推奨設定: `main` のルールセット、`DIRECT_DATABASE_URL` を `production` 環境へ移すこと
- プライバシーポリシー・利用規約の法的な文面の確認

Low / Research: 中京圏など対象地域の追加、時刻移動を伴う推定枠の追跡、推定精度の評価。データ品質と保守の負担を検証してから着手する。

## 分析コンテンツの候補

数値や結論は実データから計算し、先に決めない。2005年以前の出典の登録不足など、観測データの限界を図と本文に書く。分析は `src/analysis/` に1本ずつ追加する（汎用のCMSは作らない）。

1. 深夜アニメの長期的な変遷 — 公開済み（`/analysis/late-night`）
2. 制作会社・出版社から見た暗黙の放送枠 — 公開済み（実験、`/analysis/implicit-slots`）。予測は弱い（1位的中は制作会社 約9%・出版社 約19%）ため、的中率と一緒にだけ表示する
3. ノイタミナの歴代作品と放送枠の歴史 — 出典記載と公式情報を区別する。公式放送枠の整理の後
4. TOKYO MX と BS11 のアニメ編成の比較 — 比較ページ（`/compare/channels?a=mx&b=bs11`）で数値は見られる。長期の傾向をまとめた分析ページは未作成
5. アニメが最も集中する曜日・時間帯は？ — 曜日×時間帯、同時放送本数、過去クールとの比較

発展案: 関東と関西の放送時差の歴史、24時以降の放送の増減、15分以下の短編枠の変遷、放送枠の新設・終了、クール間での編成変化。

## 保留・見送り

- 英語UI: 需要が確認できるまで保留する。
- JavaScript 無効時のデータ表示: データはストリーミングで描画され、差し替えに JavaScript が必要なため対応しない。読み込み中の代わりに案内を表示する。
- 認証付きの管理画面: 運用はCLIとGitHub Actionsで行う方針のため作らない（[architecture.md](architecture.md)）。
- 時間帯を「放送中」で判定する方式（帯の前に始まり帯にかかる放送も含める）: 開始時刻で判定するほうが検索・統計と一致し、説明もしやすいため採用しない。
- Lighthouse の CI 実行: アクセシビリティは axe で毎回確認しており、性能の点数は CI の実行環境で大きく揺れるため、閾値で合否を決める用途に向かない。性能は本番相当データでの実測（operations.md の Capacity and limits）で見る。
- 主要画面の画像比較（スクリーンショットの差分テスト）: フォントの描画が CI とローカルで異なり、基準画像の維持に手間がかかる割に誤検知が多いため見送る。画面の確認は `npm run screenshots` での目視レビューを続ける。
- バックアップの週次化: 1回の取得で Neon の転送量を数百MB使うため、無料枠では月次を維持する（理由と見直す条件は operations.md）。
