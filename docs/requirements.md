『深夜アニメ放送枠観測所』 要件定義書（完全版）

1. プロジェクト概要
サービス名
深夜アニメ放送枠観測所
目的
深夜アニメの「作品」だけでなく、「いつ・どこで・どの枠で放送されたか」を横断的に検索・分析できるWebサイトを提供する。単なる番組表アーカイブではなく、放送時間、放送局、地域、放送枠、作品属性、制作体制、続編関係などを軸に、時系列・統計的に観測できることを目的とする。
コンセプト
1作品ごとの情報閲覧に加え、次のような問いに答えられるサイトにする。
•	2014年以降、木曜深夜のフジ系枠はどう変化したか
•	関東と関西で放送タイミングはどれだけ違うか
•	どの放送時間・時間帯にどのジャンルが集まりやすいか
•	どの制作会社やスタッフがどの枠（放送時間）に乗りやすいか
•	続編作品は前期と同じ曜日・同じ時間帯に残りやすいか
•	どのクールで被りが激しかったか
•	土曜24:00の放送枠に、新作アニメの放送枠が配置されている確率はどれくらいか。また、再放送も含めるとどうなるか
参考資料が「曜日×時間帯×放送局」の面で深夜アニメを整理しているのに対し、本サービスではその視点を検索可能なデータベースと可視化ダッシュボードに拡張する。

2. スコープ
2.1 対象範囲
本サービスは、日本国内のテレビ放送を主対象とする深夜アニメ分析サイトである。初期リリースでは少なくとも過去15年程度（2010年以降）を対象にし、毎クール継続更新する。
2.2 分析対象
分析対象は以下を含む。
•	放送作品
•	放送回・放送枠
•	放送局・チャンネル
•	地域区分（関東・関西など）
•	放送クール（年・季節）
•	作品属性（ジャンル、原作種別、続編種別など）
•	制作属性（制作会社、製作委員会/出資傾向、主要スタッフ）
•	統計指標（本数、被り、継続率、時間帯分布など）
2.3 非対象
初期段階では以下は必須対象外とする。
•	配信サービスだけの独占配信作品
•	海外放送
•	詳細な視聴率
•	各話ごとの詳細な内容分析
•	著作権画像の大規模収集

4. 基本方針と用語定義
4.1 深夜アニメの定義
初期既定値として、参考資料と同様に21時以降28時未満に放送されたアニメを「深夜アニメ」とみなす。UI上ではこの定義をデフォルトにしつつ、将来的にはユーザーが時間帯閾値を変更できるようにする。参考資料では東京圏（民放キー局5局＋MX＋NHK）を基準にし、ショートアニメは10分以下、新番中心、再放送除外として整理している。（ここで30分アニメと15分アニメでも分けたいので、命名を要検討。15分アニメ：ハーフアニメと呼んで、0.5カウントするか（30分アニメは1カウント））
4.2 放送日の扱い
深夜帯は日付をまたぐため、システム内部では次の2種類を持つ。
•	実日時刻（JSTのtimestamp）
•	アニメ文脈の放送日・放送時刻（例: 月曜25:30）
これにより、「月曜深夜」という文化的な見え方と、厳密な時刻計算の両方に対応する。
4.3 カウントの定義
サイト上の「本数」は文脈により意味が変わるため、少なくとも以下を区別する。
•	作品本数: 同一作品を1として数える
•	放送件数: 作品×局×日時の組を数える
•	初回放送本数: ある地域・あるクールでの初回のみ数える
•	枠占有数: 放送枠単位で数える
ユーザーが何を数えているかを常に明示する。
4.4 放送枠の定義
放送枠は本サービスの中核概念とする。
公式名称を持つ枠（例: ノイタミナ）だけでなく、参考資料が指摘するような“事実上の放送枠”も扱う。したがって枠マスタは以下を持つ。
•	公式枠
•	通称枠
•	推定枠
•	一時的枠
•	消滅枠
また、枠には「局」「曜日」「代表開始時刻」「継続期間」「別名」「判定ルール」「信頼度」を持たせる。参考PDFでも、正式名称のある枠に加えて「水曜KADOKAWA枠」「僧侶枠」等の事実上の枠が多数存在するとされている。（要するに、正式に放送枠として設定されておらずとも、ある時間にはこの制作会社・ジャンルのアニメが放送される、という暗黙の了解が存在する場合がある）

7. データ取得要件
しょぼいカレンダーの公式仕様では、HTML以外の出力として rss.php、rss2.php、db.php、json.php、および更新時間通知の proginfo.xml、titleinfo.xml、chinfo.xml が案内されており、bot向けには「HTMLのスクレイピングはしない」「リクエストを減らす工夫をする」ことが明記されています。さらに db / rss / rss2 / json は1リクエスト/秒に制限され、無駄な高頻度アクセス、User-Agent未設定、1時間500件超、1日1万件超などではより厳しい制限対象になります。したがって本サービスは、HTMLスクレイピングではなく公式の非HTML出力を使うことを必須要件とする。
7.1 取得元
主取得元は、しょぼいカレンダーの公式非HTML出力とする。
補助的に、メタデータ不足分を埋めるための補完ソース層を持つ。
7.2 バックフィル
初回構築時に過去15年程度のバックフィルを行う。
実装上は年・月・クール単位で分割取得し、再実行可能な形にする。
7.3 差分更新
定期更新は次の組み合わせで行う。
•	放送時間更新通知の監視
•	タイトル更新通知の監視
•	チャンネル更新通知の監視
•	直近期間の再取得
•	クール切替タイミングの広めの再同期
7.4 取得方式
db.php の ProgLookup は1回のリクエストで最大5,000件までであり、全件取得には StTime / Range / LastUpdate で対象を分割する必要がある。db.php はタイトル、放送時間、チャンネル、チャンネルグループなどの生データ取得向きで、rss2.php は番組表と同系統の出力で高速・低負荷・7日以内の取得に向く。よって、初期バックフィルは db.php 中心、日常更新は更新通知XML + rss2/json 補助の構成を推奨する。
7.5 メタデータ補完
公開仕様で確認できる主な項目は、作品側では Title, ShortTitle, Cat, FirstYear, Keywords, Comment, SubTitles、放送側では TID, PID, ChName, ChID, ChGID, Count, SubTitle, Flag, StTime, EdTime などである。一方で、少なくとも公開仕様上の主要フィールド一覧からは、ジャンル・制作会社・スタッフ・続編種別をそれぞれ専用の第一級フィールドとして扱っている形は確認しにくい。そのため、これらは補完DBまたは手動編集を前提に要件化する。なお Cat は粗いカテゴリ値で、アニメ・再放送・OVA などの区別には使えるが、細かい“ジャンル”の代替にはならない。
7.6 地域判定
しょぼいカレンダー側ではチャンネルIDやチャンネルグループIDは取得できるため、それを元に本サービス内で地域マスタを持ち、関東/関西/中京/BS/CS などへ内部的に正規化する。
7.7 再放送・新番判定
rss2.php や放送フラグ仕様では 新 / 終 / 再 / 注 などの情報が利用できるため、再放送除外や新番抽出の基礎判定に使う。ただし完全ではない前提で、例外補正できるようにする。
7.8 取得実装上の必須条件
•	独自User-Agentを設定する
•	1 req/sec以下を守る
•	バーストを避ける
•	失敗時は指数バックオフ
•	差分取得は冪等にする
•	取得ログを保存する
•	元データの生保存と正規化後データを分離する

8. 放送枠判定要件
参考PDFでは、公式枠だけでなく“事実上の放送枠”も分析対象として価値があるとされているため、本サービスでも放送枠判定ロジックを持つ。
8.1 枠判定の種類
•	明示的枠: 公式名称あり
•	準明示的枠: コミュニティで通称が定着
•	推定枠: 同局・同曜日・同時間帯・継続期間などから推定
•	一時イベント枠: 短期だけ存在
8.2 枠判定ルール
枠判定は少なくとも以下の組み合わせで行う。
•	局
•	曜日
•	時刻帯
•	継続期間
•	周辺作品傾向
•	手動ルール
•	管理者補正
8.3 枠判定結果
各放送に対して以下を付与する。
•	所属枠ID
•	判定方式
•	信頼度
•	備考

9. 非機能要件
9.1 性能
•	一覧検索応答: 通常1秒以内、重い集計でも3秒以内を目標
•	グラフ描画: 初回2秒以内
•	ページ初期表示: 2.5秒以内を目標
9.2 可用性
•	更新ジョブ失敗時も閲覧機能は継続
•	取得遅延時は「最終更新日時」を明示
•	部分的欠損時もページが壊れない
9.3 データ品質
•	各フィールドにソースと更新日時を紐づける
•	自動推定値には明示ラベルを付ける
•	管理者が訂正可能
•	変更履歴を保持
9.4 保守性
•	取得層、正規化層、分析層、表示層を分離
•	放送枠判定ルールをコード直書きでなく設定化
•	メタデータ補完ソースを差し替え可能にする
9.5 法務・倫理
•	取得元の負荷を抑制
•	HTMLスクレイピングを避ける
•	データ出典を明示
•	コミュニティ編集データ由来の誤差や欠損の可能性を明示

13. このサイトで特に重要な設計判断
最後に、この企画で特に大事なのは次の4点です。
13.1 「作品DB」ではなく「放送枠DB」にする
参考PDFの面白さは、作品そのものよりも「どの曜日のどの局のどの時間に何が集まるか」にある。したがって、作品詳細よりも枠詳細と時系列変化を主役に置くべきです。
13.2 日付ではなく「アニメ時刻」を第一級にする
25:30を火曜1:30としてだけ扱うと、文化的な意味のある「月曜深夜」の分析が崩れる。
そのため、実時間とアニメ文脈時間の二重保持は必須です。
13.3 しょぼいカレンダー単独では足りない属性を前提化する
局・時刻・回数・フラグ・カテゴリ等はかなり取れるが、ジャンル・制作会社・スタッフ・続編は補完設計が要る。ここを最初から要件に入れておくと後で破綻しにくいです。
13.4 完全自動より「自動 + 手修正」
放送枠や続編関係は人間が見て直したい箇所が必ず出るので、運用画面は後回しにしない方がよいです。また、拡張性の高い実装にしてください。
